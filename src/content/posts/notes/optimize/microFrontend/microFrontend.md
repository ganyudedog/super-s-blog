## 引子
最近群友找到了一份实习，在这份实习中，他所要处理的项目中用到了 [qiankun](https://github.com/umijs/qiankun) ，这是个微前端的框架，而刚好，我这里也遇到了一个微前端项目，这个项目中采用的则是模块联邦，于是我基于两份微前端框架进行了一下比较，并探讨了一下他们各自的作用，于是就有了这篇笔记。


## 什么是微前端

微前端不是更高级的组件化，也不只是把代码拆成更多模块。组件化主要解决代码复用和 UI 拆分，微前端解决的是应用级的边界问题：一个大型前端系统可以由多个团队分别开发、构建、部署和演进，最后再在运行时或构建时组合起来。

因此，微前端关注的不只是代码组织，还包括团队边界、仓库边界、技术栈边界、发布边界、运行时组合以及故障隔离。它既可以存在于 monorepo 中，也可以由多个完全独立的仓库组成，关键不在于仓库数量，而在于子应用能否独立交付。

微前端更适合解决大型组织中的应用协作问题，而不是单纯解决“代码行数太多”。对于小团队和小项目，微前端引入的运行时加载、通信、路由、版本治理、监控和测试成本，往往会超过它带来的收益。

## 微前端的主要价值

### 独立交付

在单体前端中，一个局部改动可能触发整个应用的构建、测试和发布，发布范围和回滚范围都比较大。微前端可以把系统拆成多个独立交付单元，使每个子应用拥有自己的代码仓库或构建边界、流水线、版本和发布节奏。

这首先方便多个团队并行协同开发。团队可以围绕业务域负责自己的子应用，不需要每次修改都等待整个大仓库完成构建，也不必频繁解决所有团队同时修改同一主干带来的冲突。主应用只需要依照约定的入口、契约和版本使用子应用。

独立交付还让发布的粒度变小。一个团队可以先把新版本发布给极少量用户，观察错误率、性能和业务指标，再逐步扩大流量；也可以让不同用户群体加载不同版本来进行 A/B 测试。出现问题时，只需要下线或回滚发生问题的子应用，而不是让整个前端应用一起回滚。

不过，微前端并不必然减少 CI/CD 总成本。它只是把一部分单体构建成本转化成了应用之间的兼容性检查、联调、端到端测试、运行时降级、资源缓存和版本治理成本。对于 monorepo，增量构建、构建缓存和依赖图分析也可以解决很多全量构建问题，因此不能把微前端简单等同于“降低构建成本”。

### 独立演进

独立演进不仅是“子应用可以单独发布”，还包括子应用可以在运行时按照自己的版本被拉取。传统前端构建完成后，业务代码和依赖通常已经被打包进一个确定的产物，想替换其中的一个模块，往往需要重新构建和发布整个应用。

微前端可以把子应用的入口或远程模块作为独立资源发布。主应用在运行时根据配置、路由或版本策略拉取对应的子应用，这使得模块的更新、灰度和回滚不必与主应用绑定。对于线上小范围修复、渐进式迁移和多版本共存，这种能力尤其有价值。

运行时拉取并不意味着依赖完全不可控。生产环境仍然应该通过版本清单、依赖锁定、兼容性约束、完整性校验和回滚策略，保证每次运行使用的依赖是可追踪、可复现的。Module Federation 的共享依赖还可能根据版本协商选择宿主或远程版本，所以“运行时确定依赖”需要建立在明确的版本规则上，而不是把所有依赖交给网络请求随机决定。

不同子应用可以在一定范围内使用不同的技术栈，并且可以逐步迁移旧系统，而不必一次性重写整个前端。这对历史包袱较重、团队较多或业务边界相对清晰的系统尤其有价值。

这里的独立并不意味着完全没有约束。子应用之间仍然需要约定路由、通信、认证、权限、设计规范、依赖版本、错误处理和监控等公共契约。微前端减少的是代码和发布上的耦合，不会自动消除系统治理。

## 两个需要区分的概念：隔离与共享

微前端并不存在严格对等的“Sandbox 方向”和“Module Federation 方向”。它们解决的是不同维度的问题：

- Sandbox 主要解决应用之间如何隔离，尤其是全局变量、样式和运行时环境的冲突。
- Module Federation 主要解决模块如何被远程加载、暴露和共享。

除此之外，微前端还涉及应用组合、路由管理、生命周期、样式隔离、状态通信和独立部署等问题。因此，Sandbox 和 Module Federation 可以组合使用，也可以分别与其他方案组合，而不是互相排斥的两种架构。

可以把微前端理解成多条相互独立的能力轴：应用如何组合，模块如何加载，JavaScript 如何隔离，CSS 如何隔离，依赖如何共享，以及子应用如何独立发布。一个完整的微前端系统通常需要在这些维度上分别做出设计。

## Sandbox：以隔离为核心

Sandbox 的目标是降低多个子应用在同一页面运行时产生的冲突。以 qiankun 为例，子应用通常仍然挂载在宿主页面的某个 DOM 容器中，并不拥有真正独立的浏览器 `window` 和 `document`。qiankun 的沙箱主要分为基于 `Proxy` 的 JavaScript 沙箱，以及针对旧浏览器的快照沙箱等实现。

在支持 `Proxy` 的环境中，qiankun 会为子应用提供一个代理后的全局对象。子应用读写 `window` 上的属性时，框架可以把部分变更限制在这个代理环境内；子应用卸载时，也可以清理它在沙箱中注册的全局变量，从而减少不同子应用之间的污染。这种隔离不是创建了一个真正独立的浏览器窗口。原生 `window`、`document`、浏览器 API、网络请求和很多第三方库仍然来自同一个页面环境。对于直接操作 DOM 的代码、全局事件监听器和无法被框架接管的 SDK，仍然可能产生跨应用影响。

### CSS 隔离

qiankun 提供了两类常见的样式隔离思路。

`strictStyleIsolation` 会借助 Shadow DOM 把子应用放入 Shadow Root 中，使宿主页面和子应用之间形成更强的 CSS 边界。它的隔离效果较好，但 Shadow DOM 也会改变样式继承、弹窗挂载和第三方组件的使用方式。很多组件库会把弹窗、下拉菜单或提示层挂到 `body`，这类脱离 Shadow Root 的节点并不会自动享受同样的隔离。

`experimentalStyleIsolation` 不创建 Shadow DOM，而是改写子应用 CSS 选择器，为选择器添加类似 `data-qiankun` 的作用域限制。它对普通选择器很有帮助，但不是 CSS 语言层面的绝对隔离，涉及全局选择器、`@keyframes`、字体、通过 JavaScript 动态插入的样式、挂载到 body 的节点等情况时仍需额外处理。

因此，Sandbox 不能简单理解为“每个子应用都有一套独立的 window、store、路由和样式”。它通常只能隔离一部分 JavaScript 全局状态和 CSS 作用域；浏览器存储、DOM 事件、网络请求、第三方 SDK 和全局事件监听器仍然可能产生影响。Sandbox 方案适合异构应用共存，尤其适合接入历史项目或技术栈差异较大的子应用。代价是应用之间的共享能力较弱，通信通常依赖 props、主应用提供的公共 API、自定义事件或消息协议，依赖也可能因为技术栈或版本不同而重复加载。路由方面，主应用通常负责决定何时加载和卸载子应用，子应用再管理自己的内部路由，因此需要处理 basename、刷新、前进后退和路由冲突等问题。

## iframe：强隔离、低融合

iframe 的隔离强度更高。它不是把另一个应用挂载到当前页面的一棵 DOM 子树中，而是把另一个完整页面嵌入当前页面。它拥有独立的 `window`、`document`、JavaScript 运行时、CSS 环境、路由和存储上下文。

iframe 之所以可以被视为微前端方案，是因为微前端的关键标准是应用能否独立开发、部署、运行和组合，而不是必须共享同一套 JavaScript 运行时。一个通过 iframe 接入的子系统仍然可以由独立团队维护、独立发布，并由主应用按照 URL 或业务入口进行组合。

但 iframe 牺牲了大量融合能力。宿主页面的 `global.css` 不会自动作用于 iframe 内部，iframe 内部的样式也不会影响宿主页面；组件、hooks、路由实例和状态管理器也不能直接复用。两边可以分别加载同一份 CSS、设计令牌或静态资源，但这属于资源层面的复用，不是同一页面运行时中的共享。应用之间通常需要通过 `postMessage`、URL 参数或宿主提供的接口通信，跨域场景还会受到同源策略、安全策略和浏览器限制的影响。

除此之外，iframe 还可能带来额外的首屏加载、内存占用、网络请求、滚动与尺寸适配、SEO、可访问性和移动端体验问题。宿主和子应用的路由也天然分离，浏览器历史记录、页面标题、面包屑和统一导航需要额外协调。它因此属于强隔离、低融合的方案，更适合第三方系统接入、老旧系统集成、安全边界要求较高或几乎不需要共享运行时的场景。对于强调统一体验、共享依赖和共享设计系统的产品内部模块，通常会选择同页面挂载的方案。

## Module Federation：以运行时共享为核心

Module Federation 允许一个应用在运行时加载另一个应用暴露的模块。远程应用通过 `exposes` 暴露组件、函数或其他模块，宿主应用通过 `remotes` 或动态入口获取这些模块，并通过 `shared` 声明需要共享的依赖。

实际采用 Module Federation 的项目，大多数会选择相同或高度兼容的技术栈，尤其是相同框架和相近版本。这样做不是 Module Federation 的硬性要求，但同框架更容易共享 React、Vue、路由库、状态库和设计系统，也更容易让远程组件获得接近本地组件的使用体验。异构技术栈也可以通过 Module Federation 加载模块，但跨框架共享 hooks、Context 或组件实例通常不现实，更多时候需要通过 Web Components、标准 DOM 协议或封装后的 API 进行交互。

Module Federation 的主要价值包括：

- 远程模块可以独立构建和发布，宿主不必重新构建整个应用。
- 多个应用可以共享框架、组件库和工具库，减少重复下载和重复初始化。
- 远程组件可以像普通模块一样接收 props、调用公开方法，并复用约定好的运行时能力。
- 同一个远程模块可以被多个宿主应用消费，形成跨应用的模块复用。
- 可以在运行时切换模块版本，为灰度发布、A/B 测试和快速回滚提供基础。
- 大型团队可以围绕业务域独立维护远程模块，同时通过共享依赖和公共契约保持产品一致性。

不过，Module Federation 本身不是完整的微前端框架，也不会自动解决路由、生命周期、样式隔离、状态通信、权限、错误边界、监控和发布治理等问题。它更像一种运行时模块共享基础设施。

Module Federation 也不代表一定可以直接复用远程应用的 hooks、Context 或 Router。只有在框架、版本、运行时上下文和共享依赖都兼容时，这种复用才可靠。配置错误或存在多个框架实例时，可能出现 hooks 报错、Context 失效、路由实例不一致和状态重复等问题。通常应明确哪些依赖必须单例共享、哪些依赖允许多版本共存，以及共享失败时的 fallback 行为。

它的异步加载特性还意味着宿主必须处理加载失败、超时、版本不兼容、缓存旧资源和远程入口不可用等情况。远程模块带来的不是免费的“动态组件”，而是一套需要治理的运行时依赖关系。主应用一般负责页面级路由和子应用入口，远程模块负责业务内部路由；如果双方都直接操作浏览器历史记录，就容易出现导航冲突，因此必须明确 URL 的所有权和路由边界。

## 各种方案的边界

| 方案 | 主要解决的问题 | 核心价值 | 主要代价 |
| --- | --- | --- | --- |
| 组件化 | 代码和 UI 的复用 | 让同一应用内部更容易拆分和复用 | 没有独立部署、独立运行时和团队交付边界 |
| iframe | 页面级强隔离和异构系统接入 | 独立性最强，几乎不会发生 JS 和 CSS 污染 | 组件、样式、路由、状态和依赖难以共享，通信成本高，性能和体验成本较大 |
| Sandbox | 同一页面中多个子应用的运行时隔离 | 降低全局变量和样式冲突，适合异构子应用共存 | 隔离并不完整，依赖可能重复，通信和生命周期治理复杂 |
| Module Federation | 模块的运行时加载和依赖共享 | 子应用独立发布，同时复用框架、组件和公共依赖，接近本地模块的开发体验 | 对版本、运行时上下文、加载失败和共享契约要求较高 |

## 总结

微前端是一种应用架构：把大型前端系统拆成多个可以独立开发、构建、部署和演进的应用单元，再通过路由、运行时加载、模块共享或 iframe 等方式组合起来。

它的核心收益不是简单地减少代码量，而是建立应用级的团队和交付边界：多个团队可以并行协同开发，子应用可以独立发布、独立灰度、独立进行小流量部署和 A/B 测试，也可以在运行时拉取和切换版本。它的核心代价则是运行时复杂度、版本治理、联调测试、监控降级和用户体验一致性问题。

Sandbox 和 iframe 更偏向隔离，Module Federation 更偏向共享和运行时加载，组件化则主要解决应用内部的代码复用。它们并不是完全互斥的技术，也没有一种方案能够单独解决微前端的全部问题。真正的微前端系统，需要同时考虑应用边界、发布边界、运行时边界、路由边界和共享边界。
