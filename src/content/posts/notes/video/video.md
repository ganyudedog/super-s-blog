> 学习笔记：理解视频压缩、浏览器播放与剪辑链路时的关键概念整理。

## 一、视频为什么必须压缩

### 原始视频大到无法直接存储

解码后一帧的内存大致为：

```text
宽 × 高 × 每像素字节数
```

以 1080p、RGBA 为例：

```text
1920 × 1080 × 4 = 8,294,400 bytes ≈ 7.9 MiB / 帧
```

若以 60 fps 计算，一秒未经压缩的视频约为 `474 MiB`；一部电影会迅速达到 TB 级别。因此，无论是存储还是网络传输，视频都必须压缩。

### 突破口：相邻帧高度重复

相邻画面通常有大量重复内容。以“蓝天下的人说话”为例，背景天空基本不变，主要变化只有人物嘴部、表情或运动区域。若每帧都完整保存“天空 + 人 + 嘴”，就会重复保存大量不变数据。

视频压缩主要消除两类冗余：

- **帧内压缩（空间冗余）**：压缩单帧内部的重复信息，思路类似 JPEG。
- **帧间压缩（时间冗余）**：只记录相邻帧之间发生变化的内容，这也是 I / P / B 帧出现的原因。

### 容器与编码：最容易混淆的概念

| 概念 | 作用 | 常见示例 |
| --- | --- | --- |
| 容器（Container） | 打包视频、音频、字幕、时间戳等轨道 | MP4、WebM、MOV、MKV |
| 视频编码（Codec） | 决定视频如何压缩、解码 | H.264、H.265/HEVC、VP9、AV1 |
| 音频编码 | 决定音频如何压缩、解码 | AAC、Opus、MP3 |

同一个 `.mp4` 容器里可以放 H.264，也可以放 H.265。浏览器能否播放，取决于它是否支持**容器内实际使用的编码**，而不是只看文件后缀。这也是一些 MP4 在 Chrome 能播放、Safari 或其他环境不能播放的原因。

一个视频文件通常包含多条独立轨道：

![视频文件结构](./image/video.png)

画面与声音本来就是独立轨道，只是被容器打包在一起。这也解释了为什么可以“抽取音频”而不必重新编码视频。

## 二、I / P / B 帧

I / P / B 帧都是消除帧间重复的手段。

### I 帧：完整画面

I 帧（Intra-coded frame）独立编码，不依赖其他画面即可解码。

- 类似一张 JPEG 照片。
- 信息量与体积通常最大。
- 是解码的起点或锚点，因此也常被称为关键帧（keyframe）。

### P 帧：参考前帧的差异

P 帧（Predicted frame）不保存完整画面，只保存与前方参考帧的差异。

- 例如：“画面与上一帧相同，只有嘴部区域变化”。
- 不变的背景不需要再次完整存储。
- 必须先解出参考帧，才能还原 P 帧。
- 通常远小于 I 帧。

### B 帧：同时参考前后画面

B 帧（Bi-directional predicted frame）可以同时参考前方和后方的参考帧。

- 压缩率通常更高，体积更小。
- 解码依赖关系更复杂。
- 需要通过正确的解码顺序保证参考帧已就绪。

### GOP：画面组

GOP（Group of Pictures）是一组按固定模式排列的编码帧，通常以 I 帧作为起点：

```text
显示顺序：I  B  B  B  B  P  ...  I  B  B  B  ...
          ^                    ^
          关键帧               下一个关键帧

          <------ 一个 GOP ------>
```

P/B 帧需要参考画面才能还原。播放器需要从目标位置之前最近的可用关键帧开始，逐步解码并恢复到目标帧。

## 三、播放顺序与解码顺序

### B 帧为什么不会死锁

假设显示顺序为：

```text
I  B  B  P
```

第一个 B 帧需要参考后面的 P 帧，看上去会产生循环依赖。实际上，**解码顺序不等于显示顺序**。

| 顺序 | 帧序列 | 作用 |
| --- | --- | --- |
| 显示顺序（PTS） | `I B B P` | 决定观众看到画面的先后 |
| 解码/存储顺序（DTS） | `I P B B` | 先解出被后续帧引用的参考帧 |

解码过程如下：

1. 解码 I 帧，得到完整底图。
2. 解码 P 帧，它参考已解出的 I 帧。
3. 解码第一个 B 帧，它的前方 I 帧和后方 P 帧都已经就绪。
4. 解码第二个 B 帧。
5. 将已解码画面放入重排缓冲区（reorder buffer），再按 PTS 输出为 `I B B P`。

### 编码约束

根本规则是：一帧只能参考在**解码顺序上已经完成解码**的帧。

- 经典 IPB 编码中，B 帧通常参考已解码的 I/P 帧，且 B 帧通常不作为其他帧的参考。
- 现代编码（H.264 分层 B、H.265、AV1）允许已解码的 B 帧参与参考，但仍必须满足依赖关系无环。

编码器会在产出码流时完成依赖关系的拓扑排序。合法码流不会死锁；循环依赖只可能出现在损坏或非法码流中。

## 四、浏览器如何播放视频

### 流式播放，而不是全量解码

浏览器不会把整部视频解码为像素帧后堆在内存中。实际过程是：

```text
下载压缩码流 -> 解码为像素帧 -> 渲染 -> 丢弃已展示的像素帧
```

这里要区分两类数据：

- 被丢弃的是**解码后的像素帧**，它们非常占内存。
- 会在缓冲区或浏览器缓存中保留的是**压缩码流**，它们体积小得多。

这也是后文“回溯看过的内容通常很快”的基础。

### `<video>` 常用状态、方法与事件

| 类型 | API | 用途 |
| --- | --- | --- |
| 状态 | `duration`、`videoWidth`、`videoHeight` | 获取时长和视频尺寸 |
| 状态 | `currentTime`、`paused`、`readyState` | 读取或控制播放位置与就绪状态 |
| 方法 | `play()` / `pause()` | 开始或暂停播放 |
| 方法 | 设置 `currentTime` | Seek 跳转 |
| 事件 | `loadedmetadata` | 元数据可用，可读取时长与尺寸 |
| 事件 | `timeupdate` | 播放位置更新 |
| 事件 | `seeking` / `seeked` | 跳转开始与完成 |
| 事件 | `error` | 播放或加载失败 |


## 五、无感跳转与回溯

### 回溯不是保留了所有已解码帧

常见误区是把“解码后的帧”与“已下载的压缩数据”混为一谈。

回溯时，浏览器通常不是从内存里取回很久以前的像素帧，而是复用已缓存的压缩码流并快速重新解码。硬件解码速度较快，所以体感上像是立即回到之前的位置。

### 三种典型场景

| 场景 | 主要行为 | 体感 |
| --- | --- | --- |
| 回拖到已看位置 | 复用已缓冲的码流，从最近关键帧重新解码 | 通常很快 |
| 前拖到未下载位置 | 请求新的码流分片，再解码 | 可能出现加载等待 |
| 跳转到任意较远位置 | 定位目标位置前的关键帧，解码追帧 | 延迟取决于 GOP、网络与硬件能力 |

“看过的位置秒回、没看过的位置转圈”的体验，正说明回溯依赖的是保留的压缩码流，而不是保留所有解码帧。

### HLS / DASH 为什么能较快跳到远处

流媒体通常会：

1. 将视频切成小分片（segment）。跳到第 300 秒时，只请求目标附近的分片。
2. 让分片从关键帧附近开始，使其能够独立解码。
3. 根据网络情况使用自适应码率（ABR），先低清起播，再逐步切换到高清。

## 六、浏览器中的视频剪辑

浏览器侧通常通过播放器、WebCodecs、WebAssembly（如 FFmpeg.wasm）或业务封装库，对接浏览器或系统提供的硬件编解码能力。

基础实现可以分为两层：

- **预览层**：设置播放区间、调整 `currentTime`、叠加滤镜或画布合成，重点是交互与实时预览。
- **导出层**：对目标时间段进行解码、处理、重新编码与封装，重点是性能、内存控制和产物落盘。

仅修改播放起止时间可以非常轻量；若要求帧级精确裁剪，目标帧通常不是独立 I 帧，仍需要从前方关键帧开始解码，导出时往往还要重编码，这时候就需要接入业务封装库来对接硬件解码器，如果仅仅通过浏览器那么会非常卡顿以及大幅度占用js内存。

## 七、工业级剪辑：非破坏性编辑与延迟渲染

### 核心范式

专业剪辑软件通常不直接修改源文件：

- **非破坏性编辑（non-destructive editing）**：源视频保持不变，裁剪、拼接、转场与特效只保存为编辑决策列表（EDL）或时间线指令，也就是编辑时，如果开头帧为P帧，我直接将这里标记为到处是要转变成I帧即可，不需要重编码。
- **延迟渲染（deferred rendering）**：预览时按指令实时解码和合成，只有点击“导出”时才对完整结果进行一次编码。

```text
源媒体 + 时间线指令 -> 实时预览
源媒体 + 时间线指令 -> 导出时统一渲染与编码
```

这就是时间线可以自由拖拽入点、出点而不需要每次都切割源文件的原因：编辑阶段修改的是指令，重编码被推迟到导出阶段。

### 为什么 AE / PR 更依赖桌面硬件

- AE / PR 的压力来自多轨实时合成、特效、调色与最终重编码，通常需要桌面级 CPU、GPU、内存和磁盘吞吐。
- 移动端基础剪辑可在设备本地完成，因为手机 SoC 也包含专用编解码单元，且把大视频上传到云端会带来流量、延迟和隐私成本。
- 更重的 AI 功能，例如超分、抠像、风格迁移或生成式内容，才更可能将任务提交给后端 GPU。

## 八、结论

- **压缩**：视频通过消除空间与时间冗余压缩；I 帧保存完整画面，P/B 帧保存预测差异。
- **不死锁**：显示顺序与解码顺序可以不同，且所有参考关系必须在解码顺序上无环。
- **播放与回溯**：浏览器流式播放后丢弃像素帧，保留或复用压缩码流；回溯本质是快速重新解码。
- **精确裁剪**：目标位置往往不在关键帧上，因此常需要从前方关键帧解码并在导出时重编码。
- **工业剪辑**：核心是非破坏性编辑与延迟渲染，只在最终导出时进行一次完整编码。
